VAANIPLUS
SOFTWARE TEST PLAN
==================

Document version: 1.0
Status: Sample plan - execution results must be filled in after testing

IMPORTANT
---------
This is a realistic, project-specific test-plan draft for coursework. It is
not a test report and does not claim that any test passed. Record the actual
date, result, evidence, and defects after executing each test.

1. PURPOSE
----------

This plan describes how to verify VaaniPlus, a local-first English-Hindi
translation application with typed text, speech input, account authentication,
and per-user conversion history.

2. TEST OBJECTIVES
------------------

- Verify both translation directions: en-to-hi and hi-to-en.
- Verify typed translation and generated audio.
- Verify speech upload validation, transcription, translation, and synthesis.
- Verify account registration, sign-in, session validation, and sign-out.
- Verify conversion history retention and user isolation.
- Verify safe errors, request IDs, audio cleanup, and retry/reset behavior.
- Verify the default automated suite runs without model downloads or a GPU.
- Keep optional real-model quality checks separate from routine automated tests.

3. SCOPE
--------

In scope:
- FastAPI request validation and documented response behavior.
- Typed-text translation and text-to-speech API workflows.
- Speech-to-text and speech-to-speech API workflows.
- Mock and real provider selection behavior.
- PostgreSQL account and conversion-history behavior.
- Frontend authentication, recording, result display, playback, and recovery.
- Privacy and temporary audio-file handling.

Out of scope:
- Scientific evaluation of translation quality.
- Guaranteed processing latency or uptime.
- Mobile-native application testing.
- Languages other than English and Hindi.
- Production cloud deployment, penetration testing, or load testing.
- Real-model tests in the default automated test run.

4. TEST STRATEGY
----------------

4.1 Test levels

Unit tests:
- Validate request/response schemas, service logic, provider interfaces,
  configuration, and audio utilities.
- Use deterministic fake providers.

API/integration tests:
- Exercise FastAPI routes with the in-process test client.
- Verify response codes, payloads, headers, error formats, and provider
  interactions.
- Use isolated test databases for authentication/history tests.

Frontend/manual tests:
- Use the browser workspace and local Vite proxy.
- Verify visible behavior, microphone permissions, playback, session flow,
  responsiveness on desktop, keyboard access, and recovery messages.

Database integration:
- Start PostgreSQL 16 with Docker Compose.
- Verify account and conversion persistence and per-user history isolation.
- Do not use production or personal account data.

Optional real-model smoke tests:
- Run only when model downloads, storage, and hardware are available and
  approved.
- Clearly distinguish real model results from mock output.

4.2 Test types

- Functional testing.
- Input validation and negative testing.
- API contract testing.
- Database persistence and isolation testing.
- Browser compatibility and basic accessibility checks.
- Privacy and resource-cleanup checks.
- Optional manual real-model smoke testing.

5. TEST ENVIRONMENT
-------------------

Backend:
- Python 3.11 environment managed by uv.
- FastAPI test client and deterministic fake providers.
- Default automated tests do not require a running API server, GPU, or model
  downloads.

Frontend:
- Vite development server at 127.0.0.1:5173.
- Backend at 127.0.0.1:8000.
- Vite /api proxy configured to forward requests to the backend.
- A desktop browser with JavaScript and MediaRecorder support.

Database integration:
- PostgreSQL 16 container started from the repository root with:
  docker compose up -d postgres
- Use test-only accounts and data.

Real-model environment (optional):
- Real provider mode and required local model dependencies.
- Compatible local model runtime and available model weights.
- CUDA testing is optional and shall not block the default test suite.

6. ENTRY AND EXIT CRITERIA
--------------------------

Entry criteria:
- Test build is available and the intended code revision is identified.
- Required Python and frontend dependencies are installed.
- Test data contains no personal or production credentials.
- For database integration, the PostgreSQL test service is available.

Exit criteria:
- All required planned functional cases have an actual result recorded.
- No unresolved critical or high-severity defects remain for the demonstrated
  workflows.
- Failed or blocked cases include a reason and follow-up action.
- Automated test command and frontend build command are recorded with their
  real outputs.
- Optional real-model checks are clearly marked optional and are not confused
  with mock-provider results.

TC-012 - Per-user history retention and isolation

- Account A receives no more than its five newest records.
- Account B does not receive account A's records.

9. DEFECT MANAGEMENT
--------------------

Suggested severity levels:
- Critical: core application unavailable, data corruption, or account/history
  data exposed to another user. Stop release/demo until resolved.
- High: a major required workflow fails with no reasonable workaround.
- Medium: a feature is impaired but a documented workaround exists.
- Low: cosmetic or minor usability issue with no material workflow impact.

For every defect, record:
- Defect ID and short title.
- Steps to reproduce and expected/actual behavior.
- Environment and application revision.
- Severity, owner, status, and retest result.
- Screenshot, test output, request ID, or log evidence where appropriate.
